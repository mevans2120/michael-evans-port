# Chatbot Functionality Audit

**Date:** October 9, 2026
**Scope:** The "MEvans AI Assistant" chat in the navigation panel: suggested prompts, the `/api/chat` route, retrieval, follow-up question generation, content ingestion, logging, and the supporting infrastructure.
**Trigger:** The chatbot suggests follow-up questions it then cannot answer.

---

## 1. Summary

The reported symptom is real, but it is a side effect of a much bigger problem: **the chatbot has no knowledge base at all right now.** The Supabase project that holds the vector database no longer exists at the configured hostname. Every answer the live chatbot gives is generated from the system prompt alone, with zero retrieved context. The follow-up questions, the suggested prompts, and the "I don't have information" replies all flow from that.

Even once the database is restored, four design problems will keep producing the reported behavior:

1. The system prompt tells the model to never say it lacks information and to "make intelligent inferences," which produces confident fabrications.
2. Follow-up questions are generated by the model with no knowledge of what the corpus can answer, and the prompt explicitly asks for one question about a *different* topic than the one just retrieved.
3. The Sanity ingestion queries reference fields that no longer exist on the `project` and `profile` schemas, so case studies ingest as little more than a title and URL.
4. The suggested prompts in the CMS are never validated against the content, so an editor can publish a prompt the bot cannot answer.

There is also an unrelated **privacy finding**: the interview transcripts and resume used to build the knowledge base are publicly downloadable from the production site.

The codebase is from late 2025 and is two major versions behind on the AI SDK, uses the deprecated Edge runtime, and carries a fair amount of machinery (embeddings, hybrid search, webhooks, smart sync) that the size of the corpus does not justify. Section 6 proposes a simpler architecture.

## 2. How this was tested

| Check | Method |
|---|---|
| Live answers | Posted questions to `https://mevans.space/api/chat` with a script that reassembles the streamed text |
| Knowledge base reachability | DNS lookup and HTTPS requests against the Supabase host configured in both local and production environment variables |
| Production configuration | `vercel env pull` for production, compared against `.env.local` (hostnames only; no secrets recorded) |
| CMS content | Public GROQ queries against the Sanity production dataset for prompts, projects, blog posts, and schema field names |
| Link validity | HTTP status checks against every URL the bot emitted during testing |
| Code review | `src/app/api/chat/route.ts`, `src/components/navigation/ChatSection.tsx`, `SuggestedPrompts.tsx`, `src/lib/chatbot/*`, the Sanity webhook route, and the ingestion scripts |
| Unit tests | `npx vitest run src/lib/chatbot` |

Nothing was changed. No chat logs were read because the logging database is also unreachable.

## 3. Findings

Ranked by severity.

### F1. Critical: the vector database host does not exist

The Supabase URL configured in `NEXT_PUBLIC_SUPABASE_URL` resolves to `NXDOMAIN`. Local and production point at the same host. The REST endpoint cannot be reached at all, so `match_documents` (semantic search), the keyword search, and the `chat_logs` writes all fail on every request.

The chat route survives because `semanticSearch` and `keywordSearch` catch their errors and return empty arrays, and the logging functions return `false` on failure. The route then substitutes this string as the entire context:

```
No specific context available. Provide a general helpful response about
portfolio chatbots and suggest the user may want to add content.
```

**Evidence from the live site:**

| Question | Expected | Actual |
|---|---|---|
| "Where did Michael grow up?" | Eugene, Oregon (in transcripts) | "I don't have specific information about where Michael grew up" |
| "What is the Gag Scale?" | Summary of the blog post of that name | "This doesn't appear to be a project, tool, or concept associated with his professional background" |
| "Tell me Michael's latest work with AI" (a CMS suggested prompt) | Summary from the six AI blog posts | "I don't have specific information about Michael's most recent AI projects" |

A paused Supabase free-tier project normally still resolves in DNS, so `NXDOMAIN` suggests the project was deleted or its reference changed. This needs to be checked in the Supabase dashboard. Every other finding below is secondary until this is fixed or the chatbot is hidden.

**Related:** the unit tests pass (109 of 109), but they mock Supabase entirely, so nothing in the test suite would have caught this. The `scripts/check-production-chatbot.ts` script exists but is not run anywhere automatically.

### F2. High: the system prompt instructs the model to fabricate

The prompt in `route.ts` contains, among others:

- "NEVER say 'I don't have information' if you have ANY relevant context about the topic"
- "DO NOT apologize for incomplete context or express uncertainty"
- "Trust that the context provided is relevant and answer directly"
- "Make reasonable inferences from the context to provide comprehensive answers"
- "When asked about challenges or problems: make intelligent inferences about what problems likely existed"

Combined with `temperature: 0.8`, this produces plausible-sounding invention. Two live examples, both with no retrieved context:

**Peacock:** "His work at agencies like **Instrument and R/GA** typically involved high-impact entertainment and media clients." Instrument does not appear anywhere in the source transcripts. R/GA appears once in passing. Michael's actual agencies in the transcripts are Work & Co and Huge. This is a fabricated employment history on a professional portfolio.

**Before Launcher:** The bot described "a card-based interface with intelligent shortcuts, customizable widgets" and, when asked about challenges, invented "managing the complexity of Android's fragmented device ecosystem" and "building efficient rendering systems." The transcript describes a distraction-reduction launcher whose key feature was a notification filter that helped people open their phones 30 to 40 percent less. None of the bot's details came from the source.

The prompt's worked examples make this worse. They model answering "Michael worked on Lyft while at Work & Co" for a question where only the project name is known.

### F3. High: follow-up questions are generated blind

The prompt asks for exactly two follow-ups per answer:

> Question 1: related to the original topic. Question 2: a "learn more" style question about a DIFFERENT topic or project.

It also says "ONLY suggest questions you can confidently answer based on the context provided." These two instructions conflict. The context contains only chunks retrieved for the *current* question. The model knows nothing about what else is in the corpus except the hardcoded list of twelve case study URLs in the prompt. So Question 2 is always a guess based on a project name, and Question 1 is a guess about depth the retrieved chunks may not have.

Observed in testing:

- After the Before Launcher answer, the bot suggested "What other mobile projects has Michael worked on?" Clicking it produced "I don't have detailed information about Michael's complete mobile project history."
- After "What goes into building a successful product?", the bot suggested "How do **you** balance technical constraints with user experience goals?" The follow-ups are phrased as questions to the user, not about Michael. Sending one back to the bot is nonsensical.
- After every "I don't have information" answer, the follow-ups turn into clarifying questions ("What aspects are you most interested in?"), which the UI still renders as clickable prompts.

The UI contributes a small problem too. `parseFollowUpQuestions` in `ChatSection.tsx` extracts the questions by regex from the markdown. If the model varies its formatting (it put **Learn more** before **Follow-up questions** in one of three test answers), parsing still works, but any drift in the header text would silently drop the buttons.

### F4. High: suggested prompts are not validated against content

The three active prompts in Sanity are:

1. "What goes into building a successful product?"
2. "What is the Before Launcher?"
3. "Tell me Michael's latest work with AI"

Prompt 3 fails outright on the live site (F1). Prompt 1 is a general product-management question with no specific retrievable answer, so even with a working database it will produce a generic essay. Only prompt 2 is a good retrieval target.

Nothing in the editing flow checks whether a prompt has supporting content. The admin dashboard shows sync counts but not answerability.

### F5. Medium: Sanity ingestion queries have drifted from the schemas

`src/lib/chatbot/sanity-fetcher.ts` was written against an older content model.

**Projects.** The fetcher requests `summary`, `description`, `content`, `metrics`, `achievements`, `technologies`. The current `project` schema has `overview`, `article` (the portable text body), `featuredDescription`, `featuredMetric`, `heroSection`, `description`, `metrics`, `technologies`. There is no `summary`, `content`, or `achievements` field. The Before Launcher document, for instance, has a populated `article` and `overview` that the fetcher never reads. Case studies therefore ingest as roughly:

```
# Before Launcher
Case study URL: /case-studies/before-launcher
Category: ...
```

**Profile.** The fetcher requests `capabilities`, `sections`, `selectedProjects`, `technologies`, none of which exist. It does correctly request `bio`, `article`, `skills`, `experience`, `quickFacts`, so the profile is partially ingested.

**Blog.** The blog fetcher requests `content`, `excerpt`, `heroSection`, which match the schema. Blog ingestion is fine.

**AI projects.** The fetcher reads from `aiProject`, which has three documents, but the site's case studies and the prompt's URL list treat these as `project` documents (Post Pal appears in both). This is a content-model duplication, not a bug, but it means the same project can be ingested twice with different text.

The unit tests for the fetcher pass because they mock the Sanity client with fixtures shaped like the old schema.

### F6. Medium: hardcoded URL list in the prompt is stale and produces 404s

The prompt embeds twelve case study slugs and claims "12 case studies + 2 blog posts + about page." Reality: 13 projects, 6 blog posts.

Verified link outcomes:

| URL emitted by the bot | Status |
|---|---|
| `/case-studies/houselogic` (as written in the prompt) | **404**. The real slug is `Houselogic` with a capital H |
| `/blog/how-i-ai` (invented by the model) | **404**. The real slug is `how-i-ai-in-q4-2025` |
| `/case-studies/peacock`, `/case-studies/before-launcher`, `/about` | 200 |

The ingestion already writes "Case study URL:" and "Blog post URL:" lines into each chunk precisely so the model can copy exact links. Once retrieval works, the hardcoded list is redundant and only adds risk. It should be generated from Sanity at request time or removed.

The `LinkPreview` component renders these as cards, so a 404 link is presented with the same confidence as a good one.

### F7. Medium: source transcripts and resume are publicly downloadable

Everything under `public/chatbot-content/transcripts/` is served by Next.js as a static asset. Confirmed on production:

| File | Status |
|---|---|
| `/chatbot-content/transcripts/Michael_Evans_Resume_8_2025.pdf` | 200, 237 KB |
| `/chatbot-content/transcripts/opening_portland_office.md` | 200 |
| `/chatbot-content/transcripts/aesop_and_lyft_case_studies.md` | 200 |
| `/chatbot-content/transcripts/Personal_and_Alexander_Marchant.md` | 200 |

Several of these files have `600` permissions locally, which suggests they were considered private. There is also a `.DS_Store` in the directory and a `_Raw_Files_Ignore` subfolder; the ingestion script skips the raw folder, but the web server does not. The ingestion script only needs filesystem access at build or script time, so these files do not need to be in `public/` at all.

### F8. Medium: no production observability

- Conversation logging writes to Supabase `chat_logs`, which is unreachable (F1). Failures are logged with `console.error` and swallowed.
- The admin chat-logs API route returns 404 unless `NODE_ENV === 'development'`, so there is no way to review real conversations in production even when the database works.
- Admin routes authenticate with `ADMIN_API_TOKEN`, which is **not set** in the production Vercel environment (`NEXT_PUBLIC_ADMIN_PASSWORD` is set instead, and only for Development). The production sync-status endpoint therefore always returns 401.
- `vercel logs` returned nothing useful, and no alerting exists for the "Semantic search error" path.

The result is that the knowledge base could disappear, as it did, without any signal.

### F9. Low: assorted code issues

None of these are urgent, but they are worth fixing in the same pass.

- `route.ts` hardcodes `temperature: 0.8` while `CHATBOT_CONFIG.CHAT_TEMPERATURE` exists for that purpose.
- `rerankResults` resets every result's score to `1.0` and applies heuristic multipliers, discarding the similarity and keyword scores computed by `hybridSearch`. Only the stable-sort tie-breaking preserves the original order.
- `keywordSearch` runs an `ilike '%<whole normalized query>%'` as an "exact match" step. This almost never matches a multi-word query and costs a sequential scan.
- `chunkText` splits on raw character offsets (800 chars, 200 overlap), cutting words and sentences mid-way. Sentence or paragraph aware chunking retrieves better.
- `messageText` is taken from `lastMessage.parts?.[0]?.text`, so a multi-part message would lose everything after the first part.
- `supabaseAdmin` is exported eagerly at module load and will be `null` in any environment where env vars load late, while `getSupabaseAdmin()` exists for the lazy case. Both are used in different files.
- `searchSimilarDocuments` in `supabase.ts` is dead code with a different default threshold (0.7) from the live path (0.25).
- `ChatSection.tsx` fetches the suggested prompts from Sanity in a client-side `useEffect`, adding a request waterfall after hydration. The public layout already fetches footer data server-side and could pass the prompts the same way.
- The welcome message object uses `content` while real messages use `parts`; the render path handles both, but it is a leftover from AI SDK 4.
- The prompt still carries ~50 lines of commented-out ASCII art instructions and `detectPraise` still runs on every request for a disabled feature.

## 4. Why the follow-ups fail, in one picture

```
User question
     │
     ▼
Retrieve chunks for THIS question ──► (currently: nothing, DB is gone)
     │
     ▼
Model writes answer + 2 follow-ups
     │   Prompt says: Q2 must be about a DIFFERENT topic
     │   Model only knows: this question's chunks + 12 slugs
     ▼
Follow-up is a guess ──► user clicks ──► retrieval finds nothing ──► "I don't have..."
                                                  │
                                                  ▼
                                   Prompt says: never say that; infer instead
                                                  │
                                                  ▼
                                   Fabricated answer with a confident tone
```

Fixing F1 removes the "nothing" branch. Fixing F2 and F3 removes the guess-then-fabricate loop. Both are needed.

## 5. Recommendations

### Phase 0: stop the bleeding (do first, same day)

1. **Check the Supabase project.** Log into the Supabase dashboard and confirm whether the project exists. If it was deleted, decide between restoring Supabase (Section 6, Option A) or replacing retrieval entirely (Option B).
2. **Until retrieval works, hide the chatbot or switch it to an honest fallback.** A one-line change in `route.ts` can detect the empty-context case and return a fixed message pointing to the about page and contact form, instead of inventing an answer. Fabricated employment history (F2) is worse than no chatbot.
3. **Move the transcripts out of `public/`** (F7). A folder such as `content/chatbot/transcripts/` at the repo root is readable by the ingestion script and never served. Update the path in `ingest-content.ts`. If the resume PDF is meant to be public, link to it deliberately from the about page instead.
4. **Set `ADMIN_API_TOKEN` in the production environment** so the sync-status endpoint works (F8).

### Phase 1: make the model honest (small prompt and code changes)

5. **Rewrite the honesty section of the system prompt.** Replace the "never say you don't have information" and "make inferences" instructions with: answer only from the provided context; when the context does not cover the question, say so in one sentence and offer the closest topic you *do* have; never invent employers, clients, dates, features, or metrics. Keep the tone and format guidance.
6. **Lower temperature to 0.2 or 0.3** and read it from `CHATBOT_CONFIG`.
7. **Remove the hardcoded URL list and the "12 case studies + 2 blog posts" claim.** Build a short "available pages" manifest from Sanity at request time (titles plus slugs for projects and posts) and include it in the prompt. This fixes the 404s in F6 and gives the model an accurate map of what exists.
8. **Generate follow-ups from what is known to be answerable**, using one of these approaches:
   - *Simplest:* add a `suggestedQuestions` array field to the `project` and `blog` schemas (and a `questions` block at the top of each transcript file). Ingest them with the content. Tell the model to pick follow-ups **only from the suggested questions attached to the retrieved chunks**. Editors control the question bank; the model only chooses.
   - *More robust:* after the model proposes follow-ups, run each one through retrieval on the server and drop any whose top similarity is below a threshold before streaming. This costs two embedding calls per answer, which is negligible.
9. **Validate CMS suggested prompts.** Add a small admin check (a button in the existing chatbot-content dashboard, or a script) that runs each active prompt through retrieval and flags any with weak matches. Replace "Tell me Michael's latest work with AI" with something specific like "What's in Michael's 'How I AI' Q4 2025 post?" and replace the generic product-management prompt with a concrete one.
10. **Use structured output instead of regex-parsing markdown.** AI SDK's `Output.object` (or `generateObject` for the trailing metadata) can return `{ answer, links[], followUps[] }` so the UI never depends on the model writing `**Follow-up questions:**` exactly.

### Phase 2: fix the content pipeline

11. **Align `sanity-fetcher.ts` with the current schemas** (F5): for projects read `overview`, `article`, `featuredDescription`, `featuredMetric`, `heroSection`, `description`, `metrics`, `technologies`; for the profile drop the nonexistent fields. Update the fixtures in `sanity-fetcher.test.ts` to the real shapes so the tests catch the next drift.
12. **Decide on `aiProject` vs `project`.** Either ingest `aiProject` with a distinct URL prefix or retire the type; today Post Pal exists in both.
13. **Switch chunking to sentence or paragraph boundaries** with a token-aware size. The corpus is small enough that chunk count is not a cost concern.
14. **Add a production smoke test.** The existing `scripts/check-production-chatbot.ts` or `comprehensive-chatbot-test.ts` can be run from a Vercel cron or GitHub Action on a schedule: post the active CMS prompts to `/api/chat` and fail if any answer contains "I don't have" or if retrieval returned zero chunks. This would have caught F1 the day it happened.

### Phase 3: modernize the stack

See Section 6 for the architectural choice. Independent of that choice:

15. **Drop `export const runtime = 'edge'`** from `/api/chat` and `/api/admin/chat-logs`. The Edge runtime is deprecated on Vercel; streaming works on the default Node.js runtime with Fluid Compute, and you regain full Node APIs and longer timeouts.
16. **Upgrade the AI SDK** from `ai@5` / `@ai-sdk/react@2` to the current major (7.x at time of writing). It requires Node 22 and ESM, both of which this project already satisfies. Expect changes to `useChat` and message part handling; the welcome-message shim and `convertToModelMessages` call will need review. Verify against the installed package docs under `node_modules/ai/docs/` rather than memory.
17. **Route models through Vercel AI Gateway** (`"anthropic/claude-haiku-4-5"` style strings) to get request logging, fallbacks, and spend visibility without code for each provider. Keep Haiku 4.5 as the default for cost, with a flag to try Sonnet 5.5 for answer quality.
18. **Replace Supabase chat logging** with something that cannot silently disappear: Vercel runtime logs plus a lightweight analytics event per conversation is enough for a portfolio. If you keep a database, make the admin logs route available in production behind the token.

## 6. Architecture options for retrieval

The whole knowledge base is small. The sixteen transcript files total about 117 KB, roughly 18,500 words or 25,000 to 30,000 tokens. The Sanity content (13 projects, 6 posts, 1 profile) adds perhaps 15,000 to 25,000 tokens once the ingestion fields are fixed. Call it 50,000 tokens all in.

### Option A: restore the existing RAG pipeline

Re-provision Postgres with pgvector, ideally through the Vercel Marketplace (Supabase or Neon) so credentials are injected automatically. Run the existing `database-schema.sql`, re-run `npm run ingest -- --clear`, and reconnect the Sanity webhook.

- **Pro:** everything in the repo already targets this shape; it is a configuration fix plus Phase 1 and 2 changes.
- **Pro:** scales if the corpus grows by an order of magnitude.
- **Con:** keeps five moving parts (embedding API, vector DB, hybrid search, webhook, smart sync) for a corpus that fits in a single prompt. Each is a thing that can break silently, as this audit shows.
- **Con:** retrieval quality depends on chunking and thresholds; the prior evaluation docs from October 2025 show about 60 percent of failures were retrieval misses even when the database was healthy.

### Option B: no vector database; whole corpus in the prompt with caching (recommended)

Load the full corpus (transcripts plus a Sanity export) into the system prompt as a single cached block. Use Anthropic prompt caching so the ~50k token corpus is written once and read from cache on subsequent requests. Regenerate the corpus file at build time or on the Sanity webhook; no embeddings, no database.

- **Pro:** eliminates F1 structurally. There is nothing to go unreachable.
- **Pro:** retrieval misses disappear. The model sees everything, so "Where did Michael grow up?" and "What is the Gag Scale?" are answered directly.
- **Pro:** follow-up questions become trivially honest: the model can see the whole corpus and the prompt can say "only ask about things in this document."
- **Pro:** removes roughly 1,500 lines of code and three services (Supabase, Google embeddings, webhook sync).
- **Con:** per-request cost rises. At current Haiku 4.5 list pricing, a 50k-token cached read is on the order of half a cent per message; uncached writes happen once per cache window. Verify against current pricing before committing. For a portfolio chatbot this is very likely cheaper than the Supabase plus embedding spend it replaces, but it should be checked.
- **Con:** latency to first token rises slightly with a larger prompt, though caching keeps this small.
- **Con:** stops being viable if the corpus grows past a few hundred thousand tokens. At that point move to Option A or a hybrid where a cheap first pass picks which documents to include.

### Option C: hybrid

Keep the corpus as a set of 20 to 30 whole documents (one per transcript, project, and post) rather than 800-character chunks. On each request, embed the question, pick the top three to five *documents* by similarity, and include them whole. This keeps the database but makes retrieval far more forgiving, since a document either matches or not. It is a reasonable middle path if Option B's token cost turns out to matter.

**Recommendation:** Option B. The corpus is small, the failure mode of Option A has already happened once, and the honest follow-up behavior the user is asking for falls out naturally when the model can see the whole corpus. Keep the ingestion code path that assembles text from Sanity (fixed per F5), but have it write a single corpus file instead of embeddings.
